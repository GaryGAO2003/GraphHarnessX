% =========================================================================
\chapter{GraphHarnessX: A Graph-Native Harness Runtime}
\label{ch:ghx}
% =========================================================================

\claim{Execution becomes a first-class, machine-queryable object, attached
to the unmodified official loop from outside --- with the readout ladder as
the system's organizing frame and campaign-level mechanism observations tied
to their recorded evidence.}

Chapter~\ref{ch:baseline} established that the loop's evidence about its
own execution is wrong in a way that follows from how it is computed. This
chapter describes the system built in response. GHX makes the execution
itself a recorded, typed, queryable object, so that a question about what
happened during a run can be answered by reading a graph rather than by
pattern-matching over text.

Each section states what was built and what it is entitled to claim.
\S\ref{sec:construction-limits} collects the limitations that follow from
the construction itself, stated here rather than in the threats section.

\section{Design constraints}
\label{sec:constraints}
% -------------------------------------------------------------------------

Figure~\ref{fig:loop} places each implemented GHX mechanism against its
attachment stage and shows the readout framework separately. Five constraints
were fixed before any code was written.

\begin{figure}[t]
\centering
\resizebox{\textwidth}{!}{\input{figures/loop.tex}}
\caption[The released loop and where GHX attaches]{The released
loop (solid) and the seams at which GHX attaches (dashed).
The recorder writes the composition graph and the unfolded execution
DAG while the solver batch runs; cone evidence enters the Digester's and
Planner's context through a recorded injection manifest; candidates
become typed candidate operations; a sixth gate runs after the five official
gates and records its replay check. The separate readout framework distinguishes R0
deployment status, R1 pre-landing replay, R2 post-landing firing and manually
exercised R3 efficacy; R3 was not wired into retention. With every flag off the dashed boxes are absent and
the loop is byte-for-byte the released one.}
\label{fig:loop}
\end{figure}

\begin{itemize}
  \item \textbf{Byte-pinned substrate.} The official tree is vendored at a
        fixed revision under a sha256 manifest enforced by the test suite,
        so the baseline arm runs the authors' system and no between-arm
        difference is confounded with maintenance.
  \item \textbf{Zero core edits.} No byte of that tree is modified; every
        GHX mechanism attaches at a seam, which is what makes the first
        constraint checkable.
  \item \textbf{Seams restore in \texttt{finally}}, unconditionally, so a
        crash leaves no modified loop for the next round to inherit.
  \item \textbf{Flags default off}, so arm separation is a property of the
        configuration rather than of operator discipline: a campaign flown
        with no flags set behaves as the official system.
  \item \textbf{Gates require recorded rejection tests.} Every gate
        added here is mutation-tested --- a deliberately malformed
        candidate must be refused and the refusal recorded --- before it
        counts as existing.
\end{itemize}

\section{The typed executable composition graph}
\label{sec:composition-graph}
% -------------------------------------------------------------------------

GHX represents harness composition and observed execution with linked
graphs. The composition exporter re-expresses the processor pipeline as
the typed graph $G$: the schema defines six node types, while the current
exporter materializes the three used here --- fixed runloop hook points,
processors, and declared or runtime slots. Bundles, skills, and tools remain
schema categories rather than static nodes produced by this exporter. Tool
calls and nested-agent events appear in the unfolded execution graph $U$.

Two properties are enforced by test. The first is ordering: for processors
represented in $G$, graph-derived \texttt{EXECUTES\_BEFORE} chains are the
ordering authority, and a processor the exporter cannot represent is marked
\texttt{UNGRAPHED} and appended in registration order. The second is parity:
a \textbf{parity door} checks the resulting dispatch against the legacy
runloop --- given the same inputs, the graph-driven and original paths must
produce a byte-identical dispatch sequence.

\subsection*{Additional properties of the graph representation}


\begin{enumerate}
  \item \textbf{The graphed processor surface and its execution share
        a coordinate system.} $G$ and $U$ share identifiers for represented
        processors, so a candidate's claim about \emph{where} it acts can be
        checked against the graph of the run that failed. Tool calls and
        nested-agent events exist only in $U$, and registry-only edits are
        outside this shared identifier scope. Over a configuration file the
        supported comparison is not expressible --- there is no execution
        object against which to check the claimed target. This makes rungs
        R1 and R2 mechanical (\S\ref{sec:ladder}), and the sixth gate refused
        eighteen candidates that had passed all five official gates, pooled over
        three graph seeds \F{53}.
\end{enumerate}

The cost is stated where it belongs: the typed surface reaches
\emph{less} of the action space than the prose one it replaces
(\S\ref{sec:candidate-surface}), and $G$ has to be held at parity, which
is a standing test burden rather than a one-off proof.

\section{The unfolded execution graph}
\label{sec:unfolded}
% -------------------------------------------------------------------------

The composition graph describes the exported processor pipeline. The
unfolded execution graph $U$ records what one invocation did: a
directed acyclic graph over processors, tool calls, and nested agents,
written by the runtime as execution proceeds.

Acyclicity is constructive rather than checked: every event receives a
global ordinal, and edges only ever run from lower to higher, so a cycle
cannot be represented. Data edges are computed by reaching definitions ---
the last writer of a slot to each reader of it --- and cross-checked
against the runtime's own slot provenance.

Three recording rules govern the recorder, and are the reason $U$ is usable
as evidence:

\begin{enumerate}
  \item \textbf{Edges are never invented.} An edge exists in $U$ only if
        the runtime observed the dependency it represents.
  \item \textbf{An unattributable event is marked \texttt{UNGRAPHED}, not
        given a plausible identifier.} The recorder is permitted to say it
        does not know.
  \item \textbf{Cross-layer frontiers are reported, never silently
        crossed.} Where the graph's knowledge ends --- a nested agent
        boundary, an external call --- the boundary appears in the record.
\end{enumerate}

These rules reduce coverage but restrict decisions to recorded
dependencies; inferred edges would not support the same check.

\section{Identity: three nested hashes}
\label{sec:identity}
% -------------------------------------------------------------------------

For the graph-represented processor surface, three nested hashes separate
declaration from observation: \textbf{genotype} hashes persistent graph
nodes and declared edges; \textbf{deployment} adds the runtime
processor-and-slot overlay; and \textbf{phenotype} adds observed execution
edges. The containment $\text{genotype} \subseteq \text{deployment}
\subseteq \text{phenotype}$ is enforced by a hash-contract test. These are
graph identities, not complete candidate-configuration identities:
\texttt{insert\_tool} and \texttt{remove\_tool} change
\texttt{tool\_registry.custom} outside the snapshot and do not move these
hashes (40 of the 92 typed operations written, \F{63}). Registry operations remain inspectable in the generated
configuration and edit ledger; graph-hash equality alone does not establish
whole-configuration equality. The nearest precedent is the archive identity of the Darwin
G\"odel Machine~\cite{dgm}; the difference is that this layering exists to
separate \emph{declaration} from \emph{observation}, the distinction a
free-text surface destroys.

\section{Causal queries over the execution graph}
\label{sec:cones}
% -------------------------------------------------------------------------

The query the loop needs, and cannot express over flat logs, is: given this
failure, what could have produced it? In $U$ this is the \textbf{ancestor
cone} of the failing event --- everything upstream of it. The full cone
follows control and data edges; the data cone restricts to data flow alone.

The modal wording is kept throughout: the cone is what \emph{could have
shaped} the failure, never what caused it (measured sizes and one rendered
cone: Figure~\ref{fig:cone-seeds}, \F{55}). Under the recorder's honesty
rules it is a \emph{partial, observation-limited} reading of the causal
ancestry --- it contains no invented edge, and it may omit a dependency
the runtime did not observe. It is not a counterfactual and is nowhere
treated as one.

\section{Evidence integration}
\label{sec:evidence-integration}
% -------------------------------------------------------------------------

Failure cones and cross-task facts are injected into the Digester's and
Planner's context. Passing tasks enter as the \emph{contrast side} rather
than as dossiers of their own: passing-cone signatures feed the lift
control --- without them lift is explicitly not computed --- along with
flip diffs recording what a task's cone gained or lost since it last
passed. The official Digester's own digestion of all outcomes is left
untouched, so nothing downstream changes shape.

The construction-mismatched flow column of \S\ref{sec:evidence-audit} is replaced. Every
injection is recorded in a manifest, so what a role saw is established
independently of the role's own account.

A separate flag, \texttt{HARNESSX\_GHX\_PLANNER\_SENSES}, switching
independently of the injection just described, extends this seam to give
the Planner fate-bucket base rates for target selection
and the Critic the same rates for pricing predicted hits, but it stayed off
in every whitelist campaign, so its effect is unmeasured.

\section{Verification surfaces}
\label{sec:verification}
% -------------------------------------------------------------------------

Two surfaces use $U$ to check claims that previously lacked an execution-record check.

\paragraph{A sixth acceptance gate.} The official structure gate already
checks that a candidate's evidence exists, but as \emph{text}: a citation
must resolve to a file and a step index inside it. It cannot ask whether
the component a candidate says it is repairing was ever \emph{executed} on
the failure it cites, because nothing in the official record represents
execution as anything but prose. The sixth gate asks exactly that: if a
candidate says it is repairing a node, that node must appear in the graph
of the failure it claims to repair (a processor node: appear \emph{and}
intervene). Because that record is incomplete by
rule --- edges are only ever observed, never inferred --- an absent or
never-intervening node
establishes that the candidate cannot support its claim from the record,
not that the node never ran: the gate refuses \emph{unsupported} claims,
which is the only refusal the record licenses. Where no replay graph exists the gate records a pass with
\texttt{checked=False}: it passes the candidate, records that it could not
check, and never reports having checked when it did not. That default also
disarms a trap in the official ladder, whose synthetic-task smoke gate runs
a two-step task (``Reply with exactly: OK'') in which no new tool ever
fires: a gate reading \emph{that} execution would refuse every tool candidate.


\paragraph{Sixth-gate semantics.} The sixth gate refuses an edit when
the edited target has no execution record --- for a processor, no
intervention --- in the observed replay. Such a refusal establishes only
that the structural condition failed on that replay; it does not establish
candidate efficacy. The selected shipped-candidate stress test in
\S\ref{sec:localization} describes criterion outcomes within that sample.

\paragraph{What ``checkable'' names.} Checkability is not itself one of
this chapter's measured quantities; it is a label for a bundle of
independently measured facts --- the construction-mismatched flow column's dossier reach
\F{7}, the citation-density and validator observations associated with the
graph arms \F{52}, the sixth gate's kill count \F{53} and its per-campaign
refusal record
\F{11} --- each falsifiable on its own terms rather than as one
operationalised statistic.

\section{The typed candidate surface}
\label{sec:candidate-surface}
% -------------------------------------------------------------------------

Candidates become typed candidate operations, validated when authored and
rendered back into the official formats so that nothing downstream changes.

What changed is how an edit is \textbf{committed and identified}. Under the
official path, the Evolver composes a manifest and a \texttt{config.yaml}
as free text, and the candidate's real edit is whatever survived its own
transcription. Under GHX, processor-graph changes use seven operations ---
\texttt{insert\_node}, \texttt{remove\_node},
\texttt{replace\_same\_group}, \texttt{change\_dependency},
\texttt{swap\_subgraph}, \texttt{mutate\_inactive}, and
\texttt{mutate\_params}. Two registry operations, \texttt{insert\_tool}
and \texttt{remove\_tool}, change \texttt{tool\_registry.custom} outside
the graph snapshot; prompt parameters change through
\texttt{mutate\_params} on the prompt processor. A candidate may contain
graph and registry operations in one atomic transaction. Generated
artifacts and the edit ledger record the whole candidate, while
write\,$\to$\,reload\,$\to$\,re-graph checks apply to the graph surface
and do not imply that registry tools passed the graph round-trip or graph
preflight (\texttt{harnessx/ghx/graph\_proposals.py}).

A broader stored prediction union is split by machine
(\texttt{\_predicted\_split}) into a \emph{core}, whose processor-graph
targets touch the task's cone, and a \emph{halo}, whose targets do not. This population is not identical
to \texttt{tasks\_will\_unlock}, and registry-tool touches are omitted;
see \S\ref{sec:proposal-face}.

The recording rules extend into the tool text the loop reads:
\texttt{mutate\_inactive} does not verify inactivity and says so in its own
description; underscore-prefixed metadata is refused outright rather than
silently accepted.

\subsection*{Coverage}

The typed surface is \emph{narrower} than the free-text one it replaces:
seven graph operations on the processor plane, two config-section
operations for tools, prompt edits as \texttt{mutate\_params} on the prompt
processor's template, and the harness's own source out of scope entirely
--- recorded as a deviation (Appendix~\ref{app:deviations}). An edge-only
\texttt{change\_dependency} proposal is refused at finalization because
released compose carries processor-list and tool-registry changes but does
not read graph edges. GHX types a slice of the official action space rather
than extending it, and the slice is the claim.

\subsection*{The runtime policy engine}

The graph also supports rule slots the loop itself fills. A loop-authored
rule can therefore be represented, deployed, and observed through the same
runtime channel.

\section{The readout ladder}
\label{sec:ladder}
% -------------------------------------------------------------------------

The system's organizing frame, and the frame this thesis proposes for the
field, is a four-rung ladder of evidence about an edit, written
\textbf{R0}--\textbf{R3}. The rungs grade \emph{what is known about one
edit}; they are not the cumulative GHX switches of
\S\ref{sec:constraints}, which are numbered L0--L5 in the run archives and
grade what the runtime records:

\begin{itemize}
  \item[\textbf{R0}] \emph{Is it in the deployed configuration?} ---
        requires evidence from the deployed configuration; gate acceptance alone
        does not establish deployment.
  \item[\textbf{R1}] \emph{Would it have executed on the recorded failures
        it cites?} --- answered \emph{before landing} by the sixth gate,
        which replays the edited target against one selected recorded graph. After landing the question is
        subsumed by R2's fire counts; no separate post-landing execution
        check exists.
  \item[\textbf{R2}] \emph{Did it fire, and on what?} --- answered by fire
        and false-positive counts over $U$; produced by the loop itself
        \F{11}\F{38}.
  \item[\textbf{R3}] \emph{Did firing change outcomes?} --- answered by
        paired same-window trials with firing attribution; built and
        exercised \emph{by hand} in this thesis \F{34}\F{36}, and never
        wired into the loop.
\end{itemize}

\section{Limitations by construction}
\label{sec:construction-limits}
% -------------------------------------------------------------------------


\paragraph{Recorder-gated dormancy.} Runtime-rule firing depends on unfold
recording. With that recorder disabled, runtime rules are mute even when an
edit is deployed and has passed the acceptance gates. Chapter~\ref{ch:results}
reports the recorded score summaries and the separately protocolled
efficacy trial.
