% =========================================================================
\chapter{GraphHarnessX: A Graph-Native Harness Runtime}
\label{ch:ghx}
% =========================================================================

\claim{Execution becomes a first-class, machine-queryable object, attached
to the unmodified official loop from outside --- with the readout ladder as
the system's organizing frame and every mechanism claim carried by a live
record.}

Chapter~\ref{ch:baseline} established that the loop's evidence about its
own execution is wrong in a way that follows from how it is computed. This
chapter describes the system built in response. GHX makes the execution
itself a recorded, typed, queryable object, so that a question about what
happened during a run can be answered by reading a graph rather than by
pattern-matching over text.

Each section states what was built and what it is entitled to claim.
\S\ref{sec:construction-limits} collects the limitations that follow from
the construction itself, stated here rather than in the threats section.

% -------------------------------------------------------------------------
\section{Design constraints}
\label{sec:constraints}
% -------------------------------------------------------------------------

Figure~\ref{fig:loop} places every mechanism of this chapter against the
stage of the official loop it attaches to. Five constraints were fixed before any code was written.

\begin{figure}[t]
\centering
\resizebox{\textwidth}{!}{\input{figures/loop.tex}}
\caption[The six-stage loop and where GHX attaches]{The released
six-stage loop (solid) and the seams at which GHX attaches (dashed).
The recorder writes the composition graph and the unfolded execution
DAG while the solver batch runs; cone evidence enters the Digester's and
Planner's context through a recorded injection manifest; candidates
become typed graph edits; a sixth gate and a replay record sit beside the
five official gates; and the readout ladder names what is known about an
edit at commit time. With every flag off the dashed boxes are absent and
the loop is byte-for-byte the released one.}
\label{fig:loop}
\end{figure}

\begin{itemize}
  \item \textbf{Byte-pinned substrate.} The official tree is vendored at a
        fixed revision under a sha256 manifest enforced by the test suite,
        so the baseline arm runs the authors' system and no between-arm
        difference is confounded with maintenance.
  \item \textbf{Zero core edits.} No byte of that tree is modified; every
        GHX mechanism attaches at a seam, which is what makes the first
        constraint checkable.
  \item \textbf{Seams restore in \texttt{finally}}, unconditionally, so a
        crash leaves no modified loop for the next round to inherit.
  \item \textbf{Flags default off}, so arm separation is a property of the
        configuration rather than of operator discipline: a campaign flown
        with no flags set behaves as the official system.
  \item \textbf{A gate never seen to fail is not yet a gate.} Every gate
        added here is mutation-tested --- a deliberately malformed
        candidate must be refused and the refusal recorded --- before it
        counts as existing.
\end{itemize}

\section{The typed executable composition graph}
\label{sec:composition-graph}
% -------------------------------------------------------------------------

The harness's configuration is re-expressed as a typed graph. Six node
types cover the executable surface: the ten fixed runloop hook points,
processors, typed slots, bundles, skills, and tools. Twelve edge types
connect them --- ten declared or structural (attachment, ordering, declared
slot reads and writes, membership, mutual exclusion, and others) and two
observed at runtime (control and data).

Two properties are enforced by test. There is a \textbf{single ordering
authority}: the graph is the only thing that decides processor order, so
the graph and the executed pipeline cannot disagree. And there is a
\textbf{parity door} against the legacy runloop: given the same inputs, the
graph-driven and the original runloop must produce byte-identical
behaviour.

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{\input{figures/harness_graph.tex}}
\caption[The harness, graphified]{What graphifying the harness changes.
The released harness is a configuration file whose processor order is list
order plus registration side effects, and whose edits are prose
(\S\ref{sec:fielded}). GHX re-expresses the same executable surface as the
typed composition graph $G$, which then orders the running pipeline at byte
parity with the legacy runloop; each invocation of $G$ writes the unfolded
execution graph $U$, whose edges exist only where the runtime observed them
(\S\ref{sec:unfolded}). Because $G$ and $U$ name the same nodes, a claim
about where a candidate acts is checkable against the run that failed ---
the question the sixth gate asks (\S\ref{sec:verification}).}
\label{fig:harness-graph}
\end{figure}

\subsection*{What the graph buys over a configuration file}


\begin{enumerate}
  \item \textbf{The harness and its execution share one coordinate
        system.} This is the one that matters here. $U$ is an unfolding of
        $G$, so both name the same nodes, and a candidate's claim about
        \emph{where} it acts can be checked against the graph of the run
        that failed. Over a configuration file the question is not
        expressible --- there is no object in the record that a claimed
        target could be compared to. It is what makes rungs R1 and R2
        mechanical (\S\ref{sec:ladder}), and the sixth gate refused
        eighteen candidates on it that had passed all five official gates
        \F{53}.
\end{enumerate}

The cost is stated where it belongs: the typed surface reaches
\emph{less} of the action space than the prose one it replaces
(\S\ref{sec:candidate-surface}), and $G$ has to be held at parity, which
is a standing test burden rather than a one-off proof.

\section{The unfolded execution graph}
\label{sec:unfolded}
% -------------------------------------------------------------------------

The composition graph describes what the harness \emph{is}. The unfolded
execution graph $U$ records what one invocation of it \emph{did}: a
directed acyclic graph over processors, tool calls, and nested agents,
written by the runtime as execution proceeds.

Acyclicity is constructive rather than checked: every event receives a
global ordinal, and edges only ever run from lower to higher, so a cycle
cannot be represented. Data edges are computed by reaching definitions ---
the last writer of a slot to each reader of it --- and cross-checked
against the runtime's own slot provenance.

Three honesty rules govern the recorder, and are the reason $U$ is usable
as evidence:

\begin{enumerate}
  \item \textbf{Edges are never invented.} An edge exists in $U$ only if
        the runtime observed the dependency it represents.
  \item \textbf{An unattributable event is marked \texttt{UNGRAPHED}, not
        given a plausible identifier.} The recorder is permitted to say it
        does not know.
  \item \textbf{Cross-layer frontiers are reported, never silently
        crossed.} Where the graph's knowledge ends --- a nested agent
        boundary, an external call --- the boundary appears in the record.
\end{enumerate}

The rules cost coverage and buy admissibility: a gate that trusts a
guessed edge can be talked past.

\section{Identity: three nested hashes}
\label{sec:identity}
% -------------------------------------------------------------------------

A free-text edit surface confuses three questions about a candidate: is it
the same proposal as before, is it the same thing that was deployed, and
did it behave the same way. Three nested hashes separate them:
\textbf{genotype}, the structural identity of the configuration with
runtime-only processors excluded, which is the deduplication key;
\textbf{deployment}, genotype plus the runtime overlay --- what actually
ran; and \textbf{phenotype}, deployment plus the observed execution edges
--- what it actually did. The containment $\text{genotype} \subseteq
\text{deployment} \subseteq \text{phenotype}$ is nailed by a hash-contract
test. The nearest precedent is the archive identity of the Darwin
G\"odel Machine~\cite{dgm}; the difference is that this layering exists to
separate \emph{declaration} from \emph{observation}, the distinction a
free-text surface destroys.

\section{Causal queries over the execution graph}
\label{sec:cones}
% -------------------------------------------------------------------------

The query the loop needs, and cannot express over flat logs, is: given this
failure, what could have produced it? In $U$ this is the \textbf{ancestor
cone} of the failing event --- everything upstream of it. The full cone
follows control and data edges; the data cone restricts to data flow alone.

The cone is small. Over the graph campaign's early failed cohort ($n{=}56$,
rounds R0--R1), the median trajectory is a 1{,}186-node, 606{,}000-character
record, and its full cone is \textbf{48 nodes}, its data cone \textbf{42}
--- about $4\%$ of the invocation \F{55}.

The modal wording is kept throughout: the cone is what \emph{could have
shaped} the failure, never what caused it. Under the recorder's honesty
rules it is a \emph{partial, observation-limited} reading of the causal
ancestry --- it contains no invented edge, and it may omit a dependency
the runtime did not observe. It is not a counterfactual and is nowhere
treated as one.

\section{Evidence integration}
\label{sec:evidence-integration}
% -------------------------------------------------------------------------

Failure cones and cross-task facts are injected into the Digester's and
Planner's context. Passing tasks enter as the \emph{contrast side} rather
than as dossiers of their own: passing-cone signatures feed the lift
control --- without them lift is explicitly not computed --- along with
flip diffs recording what a task's cone gained or lost since it last
passed. The official Digester's own digestion of all outcomes is left
untouched, so nothing downstream changes shape.

The false flow column of \S\ref{sec:evidence-audit} is replaced. Every injection is recorded in a manifest, so what a role saw is
established independently of the role's own account.

A second, independent flag, \texttt{HARNESSX\_GHX\_PLANNER\_SENSES}, extends
this seam to give the Planner fate-bucket base rates for target selection
and the Critic the same rates for pricing predicted hits, but it stayed off
in every whitelist campaign, so its effect is unmeasured.

 By
measurement, the median rendered cone is \textbf{15.5\,kB} against the
\textbf{87.4\,kB} trajectory it competes with for the same context budget
($n{=}44$, R1) --- a ratio of \textbf{0.12} \F{55}.

\section{Verification surfaces}
\label{sec:verification}
% -------------------------------------------------------------------------

Two surfaces use $U$ to check claims that were previously taken on trust.

\paragraph{A sixth acceptance gate.} The official structure gate already
checks that a candidate's evidence exists, but as \emph{text}: a citation
must resolve to a file and a step index inside it. It cannot ask whether
the component a candidate says it is repairing was ever \emph{executed} on
the failure it cites, because nothing in the official record represents
execution as anything but prose. The sixth gate asks exactly that: if a
candidate says it is repairing a node, that node must appear in the graph
of the failure it claims to repair. Across the three graph seeds, eighteen
candidates cleared all five official gates and were then found to name a
node with no execution record in it \F{53}. Because that record is
incomplete by rule --- edges are only ever observed, never inferred --- an
absent node establishes that the candidate cannot support its claim from
the record, not that the node never ran: the gate refuses
\emph{unsupported} claims, which is the only refusal the record licenses. Where no replay graph exists the
gate records an \emph{honest pass} with \texttt{checked=False}: it passes
the candidate and records that it could not check, and never reports
having checked when it did not --- which also disarms a trap in the
official ladder, whose replay gate runs a two-step synthetic task
(``Reply with exactly: OK'') in which no new tool ever fires, so a gate
reading \emph{that} execution would refuse every tool candidate.

\paragraph{An alternative reading of the eighteen kills.} An equally
consistent reading of \F{53} is that the cone-based representation
degrades the Evolver's targeting rather than revealing targeting that was
already bad; the no-graph arm has no comparable gate or hand audit, so the
two readings are weighed, not settled, in \S\ref{sec:localization}.

\paragraph{A replay gate with a live refusal record.} Of fifteen checks,
seven produced structural refusals of the form ``edited, but never ran'',
and no refused candidate was shipped \F{11}. The refusals establish that the
gate exists in the sense of \S\ref{sec:constraints}.

Refusal correctness is unverified. Each refusal rests on a single replay draw, and no counterfactual batch was run
to establish that a refused candidate would in fact have failed. The gate
is demonstrated to fire; it is not demonstrated to fire correctly.

\paragraph{What ``checkable'' names.} Checkability is not itself one of
this chapter's measured quantities; it is a label for a bundle of
independently measured facts --- the false-flow column's dossier reach
\F{7}, the citation density and validity the graph produces \F{52}, the
sixth gate's kill count \F{53}, and the replay gate's refusal record
\F{11} --- each falsifiable on its own terms rather than as one
operationalised statistic.

\section{The typed candidate surface}
\label{sec:candidate-surface}
% -------------------------------------------------------------------------

Candidates become typed graph edits, validated when authored and rendered
back into the official formats so that nothing downstream changes.

What changed is how an edit is \textbf{committed and identified}. Under the
official path, the Evolver composes a manifest and a \texttt{config.yaml}
as free text, and the candidate's real edit is whatever survived its own
transcription. Under GHX, every mutation is one of seven typed operations
on the processor plane --- \texttt{insert\_node}, \texttt{remove\_node},
\texttt{replace\_same\_group}, \texttt{change\_dependency},
\texttt{swap\_subgraph}, \texttt{mutate\_inactive}, \texttt{mutate\_params}
--- committed as an atomic group through a five-stage transaction or
rejected whole, with both artifacts machine-generated on every call and a
write\,$\to$\,reload\,$\to$\,re-graph genotype round-trip verifying the
write (\texttt{harnessx/ghx/graph\_proposals.py}). Each card's prediction list is also split by machine into a \emph{core}
the edit touches in the task's own cone and a \emph{halo} it does not
(\texttt{\_predicted\_split}); see \S\ref{sec:proposal-face}.

The honesty rules extend into the tool text the loop reads:
\texttt{mutate\_inactive} does not verify inactivity and says so in its own
description; underscore-prefixed metadata is refused outright rather than
silently accepted.

\subsection*{Coverage}

The typed surface is \emph{narrower} than the free-text one it replaces:
seven graph operations on the processor plane, two config-section
operations for tools, prompt edits as \texttt{mutate\_params} on the prompt
processor's template, and the harness's own source out of scope entirely
--- recorded as a deviation (Appendix~\ref{app:deviations}). GHX types a
slice of the official action space rather than extending it, and the slice
is the claim.

\subsection*{The runtime policy engine}

The graph also supports rule slots the loop itself fills. The specimen is a
rule the loop authored in-run, which fired 19 times across 10 tasks with
zero collateral damage and zero conversions \F{11}\F{20} --- an aliveness
proof that the channel works end to end, from the loop's own reasoning to
a live runtime rule, and not a result.

\section{The readout ladder}
\label{sec:ladder}
% -------------------------------------------------------------------------

The system's organizing frame, and the frame this thesis proposes for the
field, is a four-rung ladder of evidence about an edit, written
\textbf{R0}--\textbf{R3}. The rungs grade \emph{what is known about one
edit}; they are not the cumulative GHX switches of
\S\ref{sec:constraints}, which are numbered L0--L5 in the run archives and
grade what the runtime records:

\begin{itemize}
  \item[\textbf{R0}] \emph{Is it in the deployed configuration?} ---
        answered by the landing gates.
  \item[\textbf{R1}] \emph{Did it ever execute?} --- answered
        \emph{before landing} by the replay gate, which refuses ``edited,
        but never ran'' against recorded graphs; live, with seven refusals,
        none of which shipped \F{11}. After landing the question is
        subsumed by R2's fire counts; no separate post-landing execution
        check exists.
  \item[\textbf{R2}] \emph{Did it fire, and on what?} --- answered by fire
        and false-positive counts over $U$; produced by the loop itself
        \F{38}.
  \item[\textbf{R3}] \emph{Did firing change outcomes?} --- answered by
        paired same-window trials with firing attribution; built and
        exercised \emph{by hand} in this thesis \F{34}\F{36}, and never
        wired into the loop.
\end{itemize}

\section{Limitations by construction}
\label{sec:construction-limits}
% -------------------------------------------------------------------------


\paragraph{Recorder-gated dormancy.} With unfold recording disabled,
runtime rules are mute. This is a silent-loss channel GHX introduces
itself: an edit can be deployed, pass every gate, and never fire, because
the recorder that would let it fire is off. It is accounted for in the
efficacy trials \F{36}, where it proved to matter.
